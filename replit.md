# Workspace

## Overview

pnpm workspace monorepo using TypeScript. Each package manages its own dependencies.

## Stack

- **Monorepo tool**: pnpm workspaces
- **Node.js version**: 24
- **Package manager**: pnpm
- **TypeScript version**: 5.9
- **API framework**: Express 5
- **Database**: PostgreSQL + Drizzle ORM
- **Validation**: Zod (`zod/v4`), `drizzle-zod`
- **API codegen**: Orval (from OpenAPI spec)
- **Build**: esbuild (CJS bundle)

## Key Commands

- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- `pnpm --filter @workspace/api-server run dev` — run API server locally

See the `pnpm-workspace` skill for workspace structure, TypeScript setup, and package details.

- **Marketplace ownership-check + buyer-balance race fix (May 2026, real-money exploit closure)**: Two distinct vulnerabilities in `/api/market/*` were closed.
  - **Exploit A (sell what you don't own)**: `/market/list` previously inserted a row from request-body fields with **zero ownership verification**. A malicious client could mint listings for non-existent planets, list the same planet twice, or re-list a sold planet — every successful "sale" would then credit ZOOM that converts to TON via the withdrawal flow (real-money loss). Fix: added `planetId` text column to `market_listings` plus a partial unique index `uq_market_seller_planet_active_sold` ON `(seller_telegram_id, planet_id) WHERE status IN ('active','sold') AND planet_id IS NOT NULL` — this is the DB-level fence that makes "sell-the-same-planet-twice" impossible regardless of client behaviour. Delisted listings are intentionally OUTSIDE the partial filter so a take-back-and-relist remains allowed. The `/market/list` handler runs in a `pool.connect()` transaction: locks the seller's user row `FOR UPDATE`, validates `planetId` exists in `users.planets_json`, validates submitted `planetType`/`planetRate` match the stored planet (blocks "list a BASIC at GOLD's price"), validates not-already-listed and not-farming, INSERTs (catches PG `23505` → 409 with seller-readable error), then surgically marks the matching planet inside `planets_json` as listed (`isListedInMarket: true`, `serverListingId`, `marketPrice`) using `jsonb_agg(CASE WHEN p->>'id'=$2 THEN p || jsonb_build_object(...) ELSE p END)` wrapped in `COALESCE(..., '[]'::jsonb)` to survive empty-array users, and bumps `planets_updated_at_ms` via `GREATEST`. `/market/buy` was extended with a same-tx jsonb removal of the sold planet from the seller's `planets_json` (best-effort cleanup; the listing row with `status='sold'` is the authoritative record and the unique index already blocks re-listing). `/market/delist` was rewritten in the same pool-tx style and clears `serverListingId`/`marketPrice` + sets `isListedInMarket:false` on the matching planet. Client `listOnMarket` now requires `planetId`, surfaces server error strings, and on rejection the `useGameState.listPlanet` callback reverts the optimistic local state and shows a destructive toast. Note: the `/regular-planets/save` endpoint still trusts the client's planets array (Fix B deferred — too invasive, would require a server-side craft ledger), so a malicious client *can* race the server's planets_json mutation by sending a higher `clientWriteAtMs` — this is acceptable because the unique-index fence on listings is what actually blocks money-impacting reuse.
  - **Exploit B (buyer balance race in `/market/buy`)**: The previous code did `SELECT zoom_balance` then `UPDATE ... SET zoom_balance = zoom_balance - totalCost` as two statements. Two concurrent buys from the same buyer could both pass the SELECT check and both deduct, driving the balance negative — effective double-spend across listings. Fix: replaced with a single conditional UPDATE `SET zoom_balance = zoom_balance - totalCost WHERE telegram_id = $1 AND zoom_balance >= totalCost RETURNING telegram_id`; if `RETURNING` is empty, ROLLBACK with `Insufficient balance`. Postgres serializes row-level writes so two concurrent buys cannot both succeed when only one is affordable.
  - **Prod deploy needs**: `ALTER TABLE market_listings ADD COLUMN planet_id text;` plus `CREATE UNIQUE INDEX uq_market_seller_planet_active_sold ON market_listings (seller_telegram_id, planet_id) WHERE status IN ('active','sold') AND planet_id IS NOT NULL;` (already applied to dev DB via drizzle push).
  - **Known remaining critical issues (NOT in this fix, reported by architect — separate work)**: (1) **No server-side auth binding** on any market endpoint — `sellerTelegramId` / `buyerTelegramId` are trusted from the request body. If/when an attacker can call the API directly (bypassing the Telegram WebApp), they could impersonate any user and move ZOOM arbitrarily. Needs Telegram `initData` HMAC verification on every money endpoint. (2) **Lock ordering inversion** between `/market/list` (locks users row → inserts listing) and `/market/buy`/`/market/delist` (touches listing row → updates users row) — Postgres deadlock detector aborts one tx safely so this is operationally noisy but not a money exploit; clients retry naturally. Standardize lock order in a future pass.
- **Vanishing-planet fix (May 2026, @lektig "10 RARE planets disappeared")**: Three independent client-side reconciliation paths could silently destroy real-money planets and then permanently persist the loss via the debounced `/regular-planets/save` whole-array replace. Root cause: each path used "shrink to match server count" semantics that fired on transient desyncs.
  - **Bug 1 (most likely root cause for @lektig)**: `applyGrants` in `useGameState.ts` ran after every `fetchGrants` (initial load, every 30s, on app-resume). When `serverCount - max(claimedCount, existingBonusCount) < 0` (e.g. server's `bonus_rare` counter dropped below the user's already-materialized count due to admin reset, race with `/planets/burn`, or GREATEST high-water-mark divergence between local `claimedBonusRare` and server's `claimed_bonus_rare`), it filtered out N `bonus-${TYPE}-*` planets from the local array. A single sync where server `bonus_rare=0` while user had 10 materialized RARE bonuses → all 10 deleted. Same code block existed twice (lines ~1577 and ~1815). **Fix**: removed the `else if (toAdd < 0)` branch entirely from both blocks. Reconciliation is now grow-only: bonus planets can only be CREATED via `applyGrants`, never deleted. Burns/sales remain the only legitimate removal paths.
  - **Bug 2**: White & Earth Collection bundle reconciliation (lines ~1733/~1758) had the same shape — when `serverBundles2 < claimedBundles2`, it filtered out collection planets by parsing the `-b{idx}-` from their id and dropping any `idx >= serverBundles2`. Same destructive pattern. **Fix**: removed both `else if` branches. Collection bundles are also grow-only now.
  - **Bug 3**: `fetchMarketListings()` in `api.ts` was returning `[]` on **every** error (HTTP non-200, network failure, JSON parse error). The periodic "orphan listing reconcile" in `useGameState.ts` (line ~2659, runs on resume + every 30s) interpreted this as "all my listed planets are gone from the market" and DELETED every locally-listed planet. A single network blip → user loses all marketplace listings. **Fix**: `fetchMarketListings` now THROWS on error so callers can distinguish a confirmed-empty market from an outage; the reconcile's `try/catch` already swallows so it bails cleanly. Other callers (`globalStore.ts` lines 79 and 160) already wrapped with `.catch()`, so no behavior change there.
  - **Defense-in-depth in the reconcile**: even when `fetchMarketListings` returns 200 with `[]` (server query bug, pagination truncation), the reconcile now (a) bails if `active.length === 0` while we have any locally-listed planet (probability of every player simultaneously delisting is effectively zero), and (b) bails with a `console.warn` if more than half of the user's listings would be wiped in a single pass (suspicious truncation). Forces a manual refresh instead of silent destruction — preferred when real money is at stake.
  - **Why it persisted to server**: every state change schedules a debounced `saveRegularPlanets` (1.2s) that whole-array replaces `users.planets_json` if `clientWriteAtMs > stored`. Any local deletion is permanent the moment the debounce fires. The four fixes above stop the deletion at the source.
  - **Server-side anti-shrink fence (defense-in-depth)**: `/regular-planets/save` now reads the stored `planets_json` first and refuses to overwrite it if the incoming array drops 6 or more items vs stored. Burns/sales remove at most ~2 planets per 1.2s debounce window, so any single save losing 6+ planets is treated as a buggy client reconciliation we haven't found yet. The endpoint logs a `[regular-planets/save] anti-shrink guard tripped for {telegramId}` warning (audit trail), still allows the GREATEST-merged `claimed_bonus_*` counters to land (they're monotonic and harmless), and returns `200 { ok:true, accepted:false, count:<stored>, rejected:"anti-shrink guard" }`. Client keeps its local state, the larger server snapshot survives, and the next legitimate operation retries cleanly. This is the last line of defense if a future client bug slips past code review.
  - **No DB schema changes**. Client fixes in `artifacts/zoom-master/src/hooks/useGameState.ts` and `artifacts/zoom-master/src/utils/api.ts`; server guard in `artifacts/api-server/src/routes/regular-planets.ts`. - **Server-side offline farming accrual + race fixes (May 2026, post-architect-review)**: Offline $ZOOM income from regular planets and the SUN is now computed and credited authoritatively by the server, not by the client. Closes the long-standing "open the app on a new device → no offline income" gap caused by the client storing the `lastFarmingSettledAt` watermark only in localStorage. New endpoint `POST /api/farm/settle` (`artifacts/api-server/src/routes/farm-settle.ts`) opens a DB transaction, locks the user row with `SELECT ... FOR UPDATE`, computes the same per-planet formula as the client (`(rate / 3_600_000) * elapsed * speedMultiplier`, capped per planet at 24h-since-`farmStartedAt` and 24h-since-`lastCollectedAt`), mirrors the +10% referral speed bonus when `referred_by IS NOT NULL`, and credits the SUN at `1000 * sunCount` ZOOM/h with the same window logic. Watermark is `max(server.last_farming_settled_at_ms, client.lastFarmingSettledAt)` so a brand-new device with no localStorage triggers credit from the per-planet timestamps, while a legacy device with an existing local watermark short-circuits to ~0 (NO double-credit on the very first server-side settle for any existing user — the migration-safety requirement). The UPDATE writes `last_farming_settled_at_ms = GREATEST(stored, now)` so the watermark is monotonic and concurrent calls cannot rewind it. `zoom_balance` is only ever incremented (no GREATEST needed; `credited` is clamped >= 0). The endpoint does not bump `balance_epoch` so client-side optimistic credits in flight (taps, wheel rewards) are not snapped down. **Client wiring** (`artifacts/zoom-master/src/utils/api.ts` + `useGameState.ts`): (1) `INITIAL_STATE.lastFarmingSettledAt` and the loader fallback are now `0` instead of `serverNow()` — fresh installs and cleared caches are recognized as "no prior local settle" so the server uses planet timestamps as the floor; the client-side `settleFarmingState`'s existing `|| now` fallback prevents an instant-24h credit on the local side. (2) `settleOfflineFarming()` runs in parallel with the existing init `Promise.all` (alongside `fetchGrants`/`fetchBalanceRecord`/`fetchRegularPlanets`); when `exists`, its post-credit `balance` supersedes the parallel `balanceRecord.zoomBalance` (which may pre-date the credit by a few ms), and `lastFarmingSettledAt` is bumped to `settleRes.settledAtMs` via `Math.max` so the watermark is monotonic. (3) Periodic `doSync` (every 30s) also calls `settleOfflineFarming` as a server-side watermark heartbeat — passes the current local watermark, server credits ~0, server's `last_farming_settled_at_ms` advances to "now". This minimizes the race window where an old device closes mid-session and a new device opens before the next heartbeat, which would otherwise let the server recredit a period the client already credited. (4) `visibilitychange` resume also fires a `settleOfflineFarming` after `settleFarmingState` so the server watermark is bumped immediately after a long Telegram-WebView background. **No DB schema changes** — relies on the already-existing `last_farming_settled_at_ms`, `planets_json`, `sun_*`, `referred_by` columns. **Migration guarantee**: no existing balance can decrease (server only adds), no watermark can rewind (GREATEST on write), and no period the client has already credited can be recredited (clientFloor as watermark floor on the very first server-side settle). Matches the user's explicit "non azzeri nulla ai membri" requirement. **Architect-review fixes** applied after the first pass: (a) `/farm/settle` now bumps `balance_epoch` whenever `credited > 0` so a near-concurrent `/balance/sync` (which writes `CASE WHEN server_epoch > clientEpoch THEN server ELSE GREATEST(0, client)`) cannot overwrite a freshly server-side credit with the pre-credit local balance — the bump forces the server-value branch and the client snaps to the post-credit balance via `reconcileFromSyncResponse`. Heartbeat calls with `credited == 0` skip the bump so we don't generate a flood of unnecessary epoch advances.
