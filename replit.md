# Workspace

## Overview

pnpm workspace monorepo using TypeScript. Each package manages its own dependencies.

## Stack

- **Monorepo tool**: pnpm workspaces
- **Node.js version**: 24
- **Package manager**: pnpm
- **TypeScript version**: 5.9
- **API framework**: Express 5
- **Database**: PostgreSQL + Drizzle ORM
- **Validation**: Zod (`zod/v4`), `drizzle-zod`
- **API codegen**: Orval (from OpenAPI spec)
- **Build**: esbuild (CJS bundle)

## Key Commands

- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- `pnpm --filter @workspace/api-server run dev` — run API server locally

See the `pnpm-workspace` skill for workspace structure, TypeScript setup, and package details.

- **ZOOM balance no longer "bounces" down on app open (May 2026)**: User reported "when I enter the app the ZOOM balance goes up, then comes back down". Root cause: client-side `settleFarmingState` (`artifacts/zoom-master/src/hooks/useGameState.ts` ~line 1195) applied a `planet.rate + Math.random() * DYNAMIC_BONUS_MAX` boost when computing offline earnings, while the server-side settle in `artifacts/api-server/src/routes/farm-settle.ts` uses `planet.rate` only (no random component). Sequence on every open:
  1. App reads cached `balance = 59662` from localStorage and renders it.
  2. Loader (~line 1335) calls `setState((prev) => settleFarmingState(prev, serverNow()))` which adds offline earnings WITH the random boost → UI jumps to e.g. `60500`.
  3. `/farm/settle` returns the deterministic server-computed total, e.g. `60362`, and bumps `balance_epoch`.
  4. The post-sync `setState` (~line 1408) takes the `epochAdvancedNow ? serverBalance` branch and snaps the visible balance to `60362` → user sees it drop from `60500` → `60362`.
  - **Fix**: replaced `planet.rate + Math.random() * DYNAMIC_BONUS_MAX` with `planet.rate + DYNAMIC_BONUS_AVG` (where `DYNAMIC_BONUS_AVG = DYNAMIC_BONUS_MAX / 2 = 5`), the EXACT formula already used by the server (`effectiveRate = rate + DYNAMIC_BONUS_AVG` in `farm-settle.ts` line 188). Now both sides credit the same number for any given window, so the post-settle epoch-snap is always a no-op and the UI never moves backwards. Applied at the single source-of-truth so all five `settleFarmingState` callsites (initial load, visibility change, foreground wake, periodic ticks, beacon flush) are fixed in one place. Architect review: SAFE TO DEPLOY.

- **Telegram initData HMAC verification on all money/state endpoints (May 2026)**: Closes the long-standing impersonation gap where `telegramId` was sent in the request body with no proof that the caller was actually that Telegram user. New helper `artifacts/api-server/src/lib/telegram-auth.ts` implements the standard Telegram WebApp validation (`https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app`): parse the `initData` query string, pop the `hash` field, sort the rest as `key=value\n` lines, compute `HMAC_SHA256(HMAC_SHA256("WebAppData", BOT_TOKEN), data_check_string)` and compare in constant time. Also enforces `auth_date` is within `TG_AUTH_MAX_AGE_SEC` (default 24h) plus a 5-min future-skew tolerance, and rejects payloads larger than 4KB (DoS guard). The verified user id is exposed on `req.tgUser.id` for downstream handlers. **Centralized policy** in `routes/index.ts`: a single `PROTECTED_ROUTES` map declares every state-modifying / money-moving endpoint and the body field that must equal the verified user id (`telegramId` for per-user endpoints, `sellerTelegramId` for `/market/list` + `/market/delist`, `buyerTelegramId` for `/market/buy`, `adminId` for every `/admin/*` endpoint). A single `router.use` middleware mounted at the top of the chain looks up the request path and applies `requireTelegramAuth({ bindField })` only on protected routes. This means new endpoints can only be added to the policy in one place — impossible to silently miss when adding a new route. Public read-only endpoints (GET) and webhook endpoints called by Telegram servers (`/stars/webhook`) are intentionally NOT protected — the former carry no secrets, the latter are authenticated by a secret-token URL. **Three modes** via `TG_AUTH_MODE` env var: `off` (disabled), `soft` (default — verify + log violations but never reject; migration-safe so already-loaded clients don't break on first deploy), `strict` (reject 401 on missing/invalid initData, 403 on bound-field mismatch). Default `soft` so any in-flight client that hasn't reloaded yet keeps working through the deploy; flip to `strict` once logs confirm clients are sending the header reliably (typically within hours since Telegram WebApp does a hard reload on every chat-button open). When `BOT_TOKEN` is missing (e.g. dev), the middleware logs a single startup warning and treats every request as unverified — combined with `soft` default, dev keeps working without secrets. **Client wiring**: `apiHeaders()` and `withInitData()` exported from `artifacts/zoom-master/src/utils/api.ts` automatically inject `X-Telegram-Init-Data: ${WebApp.initData}` on every JSON POST. So an authenticated non-admin can't impersonate an admin, AND an authenticated admin still has to be in the allow-list. **Bound-field mismatches are ALWAYS logged at warn** (not sampled) — those are the actual attack signal. Generic missing-initData failures are sampled at 1% to avoid log flooding in soft mode.
